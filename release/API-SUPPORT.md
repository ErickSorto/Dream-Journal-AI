# Store API support and separation boundaries

Checked 2026-10-23 against official Google/Apple documentation, fastlane 2.241.1 source, and the installed `google-apis-androidpublisher_v3` 0.109.0 client. This is design evidence, not a record of successful store execution. Research used no account credentials or store mutations.

## Intended stage contract

| Stage | Android | iOS |
| --- | --- | --- |
| Local plan | Deterministic selected metadata, reviewed notes, exact existing candidate, and outstanding facts. No account calls. | Same. |
| Authorized store preparation | Open a temporary edit, apply the selected changes and a production **draft**, validate, then delete the edit. No commit and no durable release/listing update. | Patch selected fields of the exact editable resources, attach the exact valid uploaded build, set and verify manual release. These are durable, separate API writes. |
| Authorized review submission | Rebuild the reviewed changes in a fresh edit; make the new candidate production release `completed`; validate; commit with `ERROR_IF_IN_REVIEW` and no fallback. Require fresh Managed Publishing and no-unrelated-pending-changes attestations. | Verify the exact version/build, manual release, reviewed content, required facts and exact submission items; submit that submission only. |
| Separately authorized public release | Play Console handoff; no automated public-release operation. | Request manual release of the exact version only in `PENDING_DEVELOPER_RELEASE`. |

Preparation is deliberately different on the two stores. Do not describe Android validation as a saved production draft, or iOS preparation as a dry run.

## Google Play: verified support and limits

- Edits are transactional for track/listing/detail mutations: uncommitted edits do not change the live app. `edits.validate` validates an edit; `edits.delete` discards it. Validation is not policy approval, and draft validation cannot prove that later `completed` submission will pass. Revalidate the actual submit payload. Read the returned `expiryTimeSeconds`; do not depend on a saved edit surviving until another action. [Edits guide](https://developers.google.com/android-publisher/edits), [validate](https://developers.google.com/android-publisher/api-ref/rest/v3/edits/validate), [delete](https://developers.google.com/android-publisher/api-ref/rest/v3/edits/delete), [expiry](https://developers.google.com/android-publisher/api-ref/rest/v3/edits)
- Opening an edit is **not read-only**: Google says a user's new edit invalidates their existing edit. Console changes or another committed edit also invalidate outstanding edits. Serialize operations sharing the relevant app/principal and stop on invalidation rather than silently rebuilding against new state. If cleanup is uncertain, report the edit ID/expiry and that discard was not confirmed. Do not claim successful discard. [Concurrency rules](https://developers.google.com/android-publisher/edits)
- A draft release does not serve its artifacts. `completed` describes the desired release configuration; it is not proof that review finished or that a release is already publicly available. Do not advance an existing staged rollout as part of this workflow. Preserve unrelated production entries, and stop if Google rejects their combination rather than deleting them automatically. [Track resource](https://developers.google.com/android-publisher/api-ref/rest/v3/edits.tracks), [draft workflow](https://developers.google.com/android-publisher/tracks#draft_releases)
- `changesNotSentForReview` is documented by Google in the rejection scenario. It is not a documented universal guarantee that arbitrary metadata writes avoid review. `changesInReviewBehavior` defaults to `CANCEL_IN_REVIEW_AND_SUBMIT`, which can cancel an existing review and send all changes for publishing. Use `ERROR_IF_IN_REVIEW`. This guard does **not** establish that there are no unrelated unsent/approved metadata changes. [Commit API](https://developers.google.com/android-publisher/api-ref/rest/v3/edits/commit)
- The installed lower-level Google client accepts `commit_edit(..., changes_in_review_behavior: "ERROR_IF_IN_REVIEW", ...)`. Supply 2.241.1 does not pass this parameter. Its default rescue may retry after removing the no-review parameter. Use the focused client path with no semantic fallback; after an uncertain commit outcome, inspect state before any retry. [Pinned Supply client](https://github.com/fastlane/fastlane/blob/2.241.1/supply/lib/supply/client.rb)
- Lifecycle read support is available: `list_application_track_releases("applications/{package}/tracks/{track}")`; response `.releases`, each with `.release_lifecycle_state` and `.active_artifacts[].version_code`. States distinguish draft, not sent, in review, approved unpublished, rejected, and published. This API returns at most 20 non-obsolete releases and does not expose all pending app metadata. Use it alongside edit-track state, not as proof of a clean Publishing overview. A published internal candidate establishes tester availability, not successful human QA. [Lifecycle resource](https://developers.google.com/android-publisher/api-ref/rest/v3/applications.tracks.releases), [list limits](https://developers.google.com/android-publisher/api-ref/rest/v3/applications.tracks.releases/list)
- No normal Play API operation to inspect/toggle Managed Publishing or execute its final **Publish changes** action was found in the current API reference. A local boolean or operator attestation is not API verification. Require fresh, explicit Console verification before submission, including absence of unrelated pending changes. Incorrect/stale attestation can permit public release after approval. Managed Publishing cannot be used for the first app publication; internal testing, changes to existing release notes, and increasing an existing staged rollout to 100% have exceptions. [API reference](https://developers.google.com/android-publisher/api-ref/rest), [Managed Publishing rules](https://support.google.com/googleplay/android-developer/answer/9859654?hl=en)
- Console submission/release handoff: open **Publishing overview**, verify **Managed publishing is turned on**, inspect all changes, then **Send for review**. Later inspect **Changes ready to publish** and choose **Publish changes** only with separate public-release authorization. [Official steps](https://support.google.com/googleplay/android-developer/answer/9859654?hl=en)

Routine fields are localized title, short/full description and video through `edits.listings`, plus contact email/phone/website through `edits.details`. Missing fields mean preserve, not clear. Avoid broad Supply promotion for preservation: it replaces destination release entries; changelog upload replaces the release-note array. [Listings](https://developers.google.com/android-publisher/api-ref/rest/v3/edits.listings), [details](https://developers.google.com/android-publisher/api-ref/rest/v3/edits.details), [pinned uploader](https://github.com/fastlane/fastlane/blob/2.241.1/supply/lib/supply/uploader.rb)

## App Store Connect: verified support and limits

- This implementation supports routine updates only. Before any preparation write it requires exactly one currently released iOS predecessor in `READY_FOR_DISTRIBUTION`. First publication, no current released predecessor, or ambiguous release state stops for Console setup; it does not manufacture initial app metadata or send first-version What's New.
- Resolve the exact app/platform/version/build and one valid result. Require `processing_state == "VALID"`; fastlane's `processed?` also accepts failed/invalid processing states. Explicit `version.select_build(build_id: ...)` is necessary during preparation: Deliver does not attach `build_number` when `submit_for_review:false`. Refetch and verify the relationship. [Pinned build model](https://github.com/fastlane/fastlane/blob/2.241.1/spaceship/lib/spaceship/connect_api/models/build.rb), [submission implementation](https://github.com/fastlane/fastlane/blob/2.241.1/deliver/lib/deliver/submit_for_review.rb)
- Set `version.update(attributes: { release_type: "MANUAL" })` and verify it independently. Deliver applies `automatic_release:false` only during metadata upload; `skip_metadata:true` skips it and an auto-release date otherwise takes precedence. Broad Deliver can also delete review attachments or phased-release/rating-reset requests and clear the demo-login-required flag. Narrow API patches preserve unrelated data. [Pinned metadata behavior](https://github.com/fastlane/fastlane/blob/2.241.1/deliver/lib/deliver/upload_metadata.rb)
- Version-localized fields include description, keywords, marketing/support URLs, promotional text and What's New. App name, subtitle and privacy-policy/choices URLs instead belong to **AppInfoLocalization** under a separate app-info resource shared across platforms. Apple documents separate live and next-release AppInfo records. Require exactly one allowed editable record by `state`; never fall back to live/latest. Privacy-policy/choices URL edits release with the next app version, unlike disclosure publishing. [Version localization model](https://github.com/fastlane/fastlane/blob/2.241.1/spaceship/lib/spaceship/connect_api/models/app_store_version_localization.rb), [AppInfo listing](https://developer.apple.com/documentation/appstoreconnectapi/get-v1-apps-_id_-appinfos), [privacy URL behavior](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy/)
- New AppInfoLocalization requires `locale` and `name`; a new version localization also needs the corresponding app-info locale. Enumerate all pages, plan both resources, and allow only reviewed locale creation with sufficient content; no invented translations. Refetch both collections after creation before creating the counterpart. Pinned `.update` maps snake_case attributes, while `create_app_info_localization` forwards raw API camelCase keys such as `privacyPolicyUrl`. [Required create fields](https://developer.apple.com/documentation/appstoreconnectapi/appinfolocalizationcreaterequest/data-data.dictionary/attributes-data.dictionary), [version-locale creation](https://developer.apple.com/documentation/appstoreconnectapi/post-v1-appstoreversionlocalizations), [pinned create helper](https://github.com/fastlane/fastlane/blob/2.241.1/spaceship/lib/spaceship/connect_api/models/app_info.rb)
- The adapter makes one limited read-only publication exception: if no AppInfo fields were selected, no pending/accepted AppInfo exists, and the only non-replaced AppInfo is live, it may use that record to validate required existing fields. This is an explicit conservative policy, not a verified guarantee about Apple's cross-resource state transitions. Selected AppInfo changes still require an unambiguous pending/accepted record; preparation never writes the live fallback.
- Patch only selected locale fields and selected reviewer contact/notes fields. Read reviewer details from the exact target version, preserving omitted demo credentials, required-login flag, notes and attachments; do not overwrite newer target values with the latest approved version's snapshot. Only confirmed absence permits creation, not authentication/network errors. Multiple Apple writes are not one transaction: report exact completed and failed steps on a partial failure, inspect uncertain outcomes before retrying, and do not automatically delete records to undo partial work. [Review-detail helper](https://github.com/fastlane/fastlane/blob/2.241.1/spaceship/lib/spaceship/connect_api/models/app_store_review_detail.rb)
- Submission must target the exact version and only its expected review-submission item. Require readiness immediately before setting `submitted:true`. Reject unrelated items and active/problem states, including cancellation/completion transitions. Pinned Deliver's polling timeout does not itself stop submission; use a fail-closed timeout. Do not rename another editable version through `ensure_version!`. [Submission implementation](https://github.com/fastlane/fastlane/blob/2.241.1/deliver/lib/deliver/submit_for_review.rb), [app helpers](https://github.com/fastlane/fastlane/blob/2.241.1/spaceship/lib/spaceship/connect_api/models/app.rb), [Apple review states](https://developer.apple.com/documentation/appstoreconnectapi/reviewsubmission/attributes-data.dictionary)
- Public release is `POST /v1/appStoreVersionReleaseRequests`, only in `PENDING_DEVELOPER_RELEASE`. Require the exact expected build and manual release type. A 201 means **release requested**, not **live**; availability can take up to 24 hours and preorder configuration matters. No verified idempotency guarantee: inspect state after uncertain responses; a generic 409 is not proof of prior success. [Release request](https://developer.apple.com/documentation/appstoreconnectapi/post-v1-appstoreversionreleaserequests), [release options](https://developer.apple.com/help/app-store-connect/manage-your-apps-availability/select-an-app-store-version-release-option/)

Apple field limits: name 2–30 characters; subtitle 30 characters; description/What's New 4,000 characters; promotional text 170 characters; keywords 100 **bytes**; reviewer notes 4,000 **bytes**. What's New is unavailable for the first version and required subsequently. [App fields](https://developer.apple.com/help/app-store-connect/reference/app-information/app-information/), [version fields](https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information/)

## Compliance boundary

Preserve existing privacy, age, content-rights, app-access and encryption declarations unless the user supplies and reviews factual changes. Unknown required facts block submission; never substitute all-false or exempt answers. Privacy-policy URLs are not privacy-disclosure questionnaires. Google has a Data Safety CSV write API, and Apple has age-rating APIs, so do not claim those are universally impossible to automate. They are intentionally outside routine field filling here. Pinned fastlane's privacy action uses Apple-ID login, can replace existing disclosures and publishes by default; do not run it as part of this API-key workflow. [Google Data Safety](https://developers.google.com/android-publisher/api-ref/rest/v3/applications/dataSafety), [Apple age APIs](https://developer.apple.com/documentation/appstoreconnectapi/age-ratings), [Apple privacy](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy/), [pinned privacy action](https://github.com/fastlane/fastlane/blob/2.241.1/fastlane/lib/fastlane/actions/upload_app_privacy_details_to_app_store.rb), [export compliance](https://developer.apple.com/help/app-store-connect/manage-app-information/overview-of-export-compliance/)
